# Shared chapter quality and release process

Applies to all books, fiction/nonfiction, and all target languages. A review is a separate pass after drafting, not a sentence saying the chapter was reviewed. No model/API service is needed. Do not force story length, simplistic language or short grammatical sentences to satisfy a metric.

## Each chapter

1. **Read context.** Check the book's guide, accepted direction, checkpoint, recent actual prose, names, chronology, possessions, unresolved threads and factual/research constraints. Resume interrupted work rather than writing it twice.
2. **Draft, then review before encoding.** Reread as a reader: place, time, who knows what, causal transitions, dialogue voices, pacing, repetition, intrigue and consequences. For nonfiction check explanations, consistency and sourced technical claims. Revise actual problems, then reread the changed scene. Review endings and transitions between chapters as well as individual scenes. Keep detailed/spoiler-bearing notes private.
3. **Encode the fixed prose.** Use sentence-sized or shorter natural clause pairs. Never use a multi-sentence paragraph as a pair, nor repeat a paragraph gloss under every sentence. Preserve source text exactly. Check every English gloss for naturalness and fidelity, and each word's gloss within its own pair. Reuse language helpers for deterministic fields. Chinese uses the finalizer, not handwritten pinyin or bands; French retains its established contextual lookup/offset contract.
4. **Validate.** Run `node tools/qa/publication.mjs prepare --chapter content/books/BOOK/ch-N.json --out /tmp/ch-N.qa.json`. This checks the actual reader JSON/catalog and produces an INCOMPLETE review template, not an automatic approval. Fix errors. Investigate every warning; a natural long sentence can be retained with a specific reason. Do not simplify prose to chase a count.
5. **Reader preview, before live publication.** Use a local/test origin so the public catalog stays unchanged. Read beginning, middle and end of EVERY chapter in the actual app; examine English guide placement, wrapping, punctuation, colours and tappable words. Inspect a saved-sentence selection and the sentence units used by dictation/Listen; do not trigger paid speech generation just to test grouping. Capture screenshots tied to the reviewed chapter. For Chinese cover pinyin and characters across the three samples. Use phone width (<=480px) per chapter, plus at least one desktop width (>=900px) per batch. Check chapter-to-chapter transitions. An unexplained stretch without meaningful English is a defect to investigate; automated sentence validity alone cannot prove good layout.
6. **Record review.** Fill the template's three review notes (`editorial`, `continuity_or_facts`, `english_alignment`) with concise spoiler-free findings/actions. Record reviewer and ISO date; list each warning code and a specific resolution. Add the three screenshot samples (beginning/middle/end, 1-based pair index, script mode, viewport width, repository-relative image path, image SHA256, actual visual findings). Put receipts at `tools/studio/qa/BOOK/ch-N.json` and screenshots under `tools/studio/qa/evidence/`. Review notes are attestations by the authoring agent, not a claim that software judges prose. Machine checks bind receipts to chapter bytes, catalog entry and renderer bytes. Any change invalidates the receipt.
7. **Checkpoint once.** Follow the book's checkpoint contract; Chinese still updates `_state.json` after each finalized chapter before writing the next. Local finalization/catalog registration is preparation, not public release. A checkpoint does not mean a chapter has passed publication QA. Preserve receipts when resuming an interrupted wave; re-review only changed material or unresolved issues.

## Batch and deployment

- Reread adjacent chapter endings/openings, continuity and pacing across the wave. No fixed arc length, no rushed quota completion, no automatic plot-summary disclosure.
- Stage only authorized files and review the staged diff. Include receipts and referenced evidence. Do not stage private plans/checkpoints, credentials or unrelated work.
- Run `node tools/qa/publication.mjs check --base <last-live-commit> --head HEAD` after committing (or `--head WORKTREE` before committing). Use the marker at `https://ww634.github.io/bilingual-reader/content/qa-release.json` to identify the last live release. Before the first gated deployment, the bootstrap baseline is `091ceaec41e127f46bdc4364edd93ac291ec2f7e`; existing content is grandfathered, not retroactively certified.
- GitHub's **Review and publish reader** workflow is the only Pages publisher. It runs tests and checks all chapter/catalog changes since the last successful public release. A later documentation-only commit cannot hide an earlier failed chapter review. Only a passing job builds/uploads the static site; a separate dependent job deploys it.
- Verify the deployed SHA, catalog versions and changed chapter bytes. Existing downloads require Browse → Update after versioned repairs. Retain existing saved cards; do not silently rewrite a reader's study material.

## What the gate checks

Identity, language and schema; matching catalog title/version/URL; nonempty glosses and alignments; one sentence or shorter per pair (language-aware punctuation/abbreviations); ordered contiguous source-word coverage; English span membership; valid categories/bands/lookup offsets; exact deterministic Chinese output; warnings for unusually long units or oversized alignment chunks; fresh chapter/catalog/renderer hashes; substantive review notes; explicit warning dispositions; actual hashed screenshot files covering each chapter's start/middle/end, scripts and phone/desktop viewports.

Screenshots and notes cannot be judged honestly by ticking boxes. The agent must view the screenshots and fix real issues. The gate verifies evidence and freshness, not literary excellence or zero layout defects. Do not claim checks you have not performed. No new test suite is required for every prose-only wave: use the shared check and focused preview; run additional tests when pipeline/reader code changes.
